# 架构与实现说明

本文回答四个问题：进程与数据怎么流动、代码怎么分层、功能做到哪一步、后续怎么扩展。

---

## 1. 进程与线程模型

```
┌──────────────────────────── WebView2（渲染进程） ────────────────────────────┐
│  React 19 应用                                                               │
│  ├─ AppProvider：唯一状态源（store / tabs / dialog / settings）              │
│  ├─ 90ms 轮询：对每个标签调 tab_snapshot(id, knownRev)                       │
│  └─ 输入：keydown → lib/keys.ts → tab_write(id, bytes)                       │
└─────────────────────────────┬────────────────────────────────────────────────┘
                              │ Tauri IPC（JSON）
┌─────────────────────────────┴────────────────────────────────────────────────┐
│  Rust 主进程                                                                  │
│  ├─ commands.rs   async 命令层（不阻塞消息循环）                              │
│  ├─ pty.rs        Runtime: HashMap<tabId, Tab>                                │
│  │                每个 Tab = PTY 主端 + 子进程 + Term + 共享写端              │
│  └─ 读线程（每标签一个）：PTY → Term::feed → 若 outbox 非空则回写             │
└─────────────────────────────┬────────────────────────────────────────────────┘
                              │ ConPTY / forkpty
                        powershell.exe / ssh / …
```

**为什么轮询而不是事件推送**：一次快照就是一份完整网格，天然幂等；`knownRev` 命中时后端只返回 `{unchanged:true}`，稳态开销很小。事件推送需要处理乱序、重放与背压，在当前规模下不划算。

**为什么写端是 `Arc<Mutex<..>>`**：读线程需要替终端回话（DSR/DA），而用户输入也走同一个写端，必须共享。

## 2. 分层与职责

| 层 | 位置 | 职责 | 可以依赖 |
| --- | --- | --- | --- |
| 数据层 | `crates/nexterm-core` | 模型、JSON 持久化、VT 解析 | 只有 serde |
| 运行时 | `src-tauri/src/pty.rs` | PTY 生命周期、读线程、尺寸同步 | core |
| 命令层 | `src-tauri/src/commands.rs` | IPC 入口、状态机、序列化给前端 | core + pty |
| 接口层 | `src/lib/api.ts` | 前端唯一的 IPC 出口 | — |
| 状态层 | `src/state/store.tsx` | 唯一状态源 + 命令分发 | api |
| 视图层 | `src/components`, `src/dialogs` | 纯展示 + 事件上报 | state |

约束：

- 组件不直接 `invoke`，全部经 `api.ts`——换 IPC 机制只改一个文件。
- `store.tsx` 不做渲染，组件不持有业务状态。
- `nexterm-core` 不引用 Tauri，因此 `cargo test -p nexterm-core` 可以脱离桌面环境跑。

## 3. 前端组件结构

```
App
├─ TitleBar            自绘标题栏（拖拽区 + 窗口按钮）
├─ MenuBar             7 个菜单，数据来自 components/menus.ts
├─ Toolbar             与菜单共用命令 id
├─ main
│  ├─ SessionPanel     搜索 / 新建 / 分组树 / 右键菜单 / 拖拽调宽
│  └─ content
│     ├─ TabStrip      标签 + 关闭 + 右键菜单
│     └─ TerminalPane  网格渲染 + 高亮叠加 + 键盘输入
│        （无标签时显示 QuickStart：标题 + 搜索 + 卡片网格）
├─ StatusBar
├─ DialogHost          按 kind 分发：session / highlight / palette / about
└─ Toaster             sonner
```

设计令牌全部在 `src/styles/index.css` 的 CSS 变量里（`:root` 与 `.dark` 两套），经 `@theme inline` 映射成 Tailwind 的 `bg-surface` / `text-fg-dim` 这类语义类名。换主题只改变量，不动组件。

## 4. 功能范围与优先级

| 优先级 | 范围 | 状态 |
| --- | --- | --- |
| **P0** | 会话 CRUD、分组、多标签、真实本地 shell、终端渲染、配色、高亮、属性对话框、菜单/工具栏/状态栏、深浅主题、快捷键 | 已完成 |
| **P1** | SSH（复用系统 `ssh`，PTY 内交互认证；密码可存系统凭据库并经 `SSH_ASKPASS` 自动应答）、会话搜索、右键菜单、标签批量关闭、拖拽调宽、强调色 | 已完成 |
| **P2** | Telnet、串口、SFTP、端口转发、按键映射、触发器、脚本、分屏、多窗口、会话导入导出 | 未实现（界面标注原因） |
| **P3** | 插件机制、多语言、崩溃上报 | 规划中 |

P2 不是"忘了"，而是在 `menus.ts::UNIMPLEMENTED` 与属性页 `todo` 里逐条写明缺什么（例如 Telnet 缺 IAC 协商、串口缺平台 COM 句柄封装），避免给出"能点但没用"的入口。

## 5. 扩展点

**加一页属性**：往 `dialogs/SessionDialog.tsx` 的 `CATEGORIES` 里加一条 `Page`，右侧表单按 `fields` 自动渲染，无需写 JSX。

**加一个命令**：`menus.ts` 加条目 → `store.tsx::runCommand` 加分支 → 需要后端就加 `commands.rs` 的 `async fn` 并注册到 `lib.rs` 的 `generate_handler!`。

**加一个协议**：`model.rs::Protocol` 加枚举值 → `pty.rs::build_command` 返回对应命令（PTY 模型下多数协议只是换一条命令行）→ 属性页加对应 `Page`。

**换存储**：`store.rs` 的 `load/save` 是唯一出入口，换成 SQLite 只影响这两个函数。

## 6. 验证方式

1. `cargo test -p nexterm-core`：12 个用例覆盖文本落格、CRLF、SGR（16 色/真彩）、光标定位、擦除、滚动与回滚、CJK 双宽、UTF-8 跨包、滚动区、DSR/DA 应答。
2. `tsc --noEmit`：前端类型零错误。
3. CDP 截图（`tools-shot.cjs`）：直接抓 WebView2 渲染层，并对 DOM 断言（终端文本、标签数量、对话框标题）。
4. 真实会话手测：本地 shell 输入命令、观察高亮着色与状态栏字节数变化。

> 调试期正是靠"断言 DOM 里有没有提示符"发现了两个真问题：命令同步执行阻塞主线程、终端不回 DSR 导致 shell 卡住。

---

## 7. 已知限制

- 终端只保留可视网格，滚轮不回看历史（`scrollback` 已收集但未在界面上暴露）。
- 没有选区与复制粘贴的原生交互（依赖系统 `Ctrl+Shift+C/V`）。
- 窗口使用自绘标题栏，未实现 Aero Snap 的拖拽到边缘吸附。
- GNU 工具链下链接会有 `.rsrc merge failure: multiple non-default manifests` 警告，不影响运行。
